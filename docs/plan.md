# Brainai 下一步计划

> 依据：GitHub Issue #1《项目背景与下一步计划》。
> 本文只读代码后产出计划，不改主干代码。计划目标是：把「修什么、怎么修、怎么验证」定清楚，再动手。

---

## 0. 结论摘要（TL;DR）

- 仓库是一份**实验记录**：1 个当前主干模型 + 大量历史迭代脚本（227 个 `.py`，约 1.8 万行）。核心要保留的只有十来份，其余是历史实验。
- **最该修的三件事（按投入产出排序）**：
  1. **缺评测自动化** —— 投入最低、产出最高，是一切改进能否被验证的前提；
  2. **声音 VQ 量化塌缩** —— 明确 bug、有现成修法、判据清晰（码本利用率）；
  3. **问答内容准确率低（约 27%，跑题）** —— 核心目标的直接体现，需先诊断再修。
- **统一模型 scaling 失败** 投入最高、且是架构级问题，`ARCHITECTURE.md` 已规划 v4 并要求「先验证三个假设」，故不排入本轮三件事，列为阶段四方向。
- 一个诚实发现：Issue 里列的 `fastvocab2.py`、`pre3.py`、`sft*.py`、`unified.py`、`uni*.py` **在当前仓库里不存在**（已用文件清单与 grep 核对）。实际对应物是 `tok_pipe.py`（词表）、`train.py`+`model.py`（统一模型）、`amae*.py`/`asem.py`（声音）。计划按仓库实际内容写。

## 1. 仓库结构梳理

### 1.1 核心（当前在用的，必须保留并继续维护）

| 文件 | 作用 |
|---|---|
| `model.py` | 统一多模态模型 `BrainNet`：视频 3D-CNN / 文本膨胀卷积 / 音频 2D-CNN → 跨模态注意力 + 三路 FiLM 融合 → 帧解码 + 字符解码 + 梅尔解码。README 记参数量约 2.1M |
| `train.py` | 训练脚本：合成/真实数据、断点续训、CSV 日志（`logs/train.csv`）、`--stage img/audio/video/all` 分阶段 |
| `eval.py` | 评测脚本：重建 MSE/PSNR、跨模态检索 R@1/R@5、生成字符准确率，产出 `logs/eval_<时间>.json/.png` |
| `data_synth.py` | 合成数据（移动几何体 + 自动描述），验证架构 |
| `data_video.py` | 从媒体库抽「视频片段 + 字幕」（ffmpeg 稀疏取帧） |
| `data_img.py` / `data_img_batch.py` | 图片数据（Flickr8k 等）准备 |
| `audio_feat.py` | 梅尔谱等音频特征 |
| `api_server.py` | Flask 服务：`/api/health /ask /caption /asr /tts` |
| `api_model.py` | 模型加载层：VLM 13.6M 图像描述、sherpa-onnx ASR、VITS TTS |
| `stream_pipeline.py` | 流式语音管道（当前用假 token 流模拟 22 token/s，测首音延迟） |
| `check_data.py` | 数据完整性检查（形状/对齐/泄漏/取值） |

### 1.2 自研基础设施（核心依赖）

| 文件 | 作用 |
|---|---|
| `tok_pipe.py` | 自研分词器：集合运算归纳（`Inducer`）+ 重要度加权；`TokLM` 用自注意力 + 重要性 bias |
| `tok_induct.py` | 归纳器实现（`tok_pipe` 依赖） |
| `tok_lm.py` | 自建小语言模型框架 |
| `tok_qa.py` | 把问答语料并入词表 |

### 1.3 历史实验 / 迭代遗留（可归档，不要继续投入）

这些文件数量大、命名带版本号，是「试错过程」的记录，不是当前产物：

- **图像描述**：`cap2.py`…`cap10.py`、`cap_merged.py`、`cap_decode_*.py`、`cap_eval_beam.py`、`vision_lm.py` —— 从贪心到 beam 到判断重排的迭代。
- **识物**：`concept*.py`（约 20 个）—— 多标签识别 + 显著性排序。
- **简笔画**：`prim_*.py`（约 30 个）、`sketch_rnn*.py`、`turtle_*.py`、`srn_*.py` —— 简笔画生成探索。
- **分阶段训练**：`stage1_*.py`、`stage2_*.py`、`stage3_*.py`。
- **中文描述**：`zh_data*.py`、`zh_train*.py`、`cn_caption*.py`。
- **声音自编码器**：`amae.py`（VQ 塌缩反面案例）、`amae2.py`（修正版）、`asem.py`（语义编码器）—— 注意：`amae2` 是当前有效的修正实现，`amae` 留作对照。

> 建议（后续可做、非本轮）：把历史实验移入 `archive/` 或打标签，README 明确「入口文件」清单，避免新人在 227 个脚本里迷失。

### 1.4 文档

| 文件 | 作用 |
|---|---|
| `README.md` | 当前架构（v3 思路）：卷积 + 跨模态注意力，无 transformer 主干 |
| `ARCHITECTURE.md` | v4 讨论稿：全局工作空间（GWS）+ 输出路由 + 自评头 + 回放；含「必须先验证的三个假设」 |

## 2. 事实基线（Issue 中「已验证的数字」）

这些数字来自 Issue，是后续改进的对照基线（本轮**不重训、不重跑**，仅作为记录；自动化评测落地后再统一复现）：

| 能力 | 指标 |
|---|---|
| 图像描述（独立 VLM，beam） | chrF 59.7% |
| 统一模型 55.8M | 图像 chrF 49.5%、声音识别 84% |
| 声音分类（CNN + mel） | 93.9% |
| 本地 ASR | 实时率 0.22、英文 WER 约 2% |
| 本地 TTS | VITS 中文 906ms、espeak 15ms |
| 端到端语音 | ASR 357ms + 模型 350ms + TTS 1040ms |

> 注意一处数字不一致：Issue 写「问答内容准确率约 27%」，但 `report_overview.py` 里写「问答（格式已学）内容准确 54.6%」。二者很可能对应不同时间点/不同评测方式。**这本身正是「缺统一评测」的体现**——数字散落在各处 print 里，无法复现。问题一的评测方案会一并解决这个口径问题。

## 3. 最该修的三个问题（按投入产出排序）

### 问题一：缺评测自动化（投入最低、产出最高）

**现状**：Issue 明确写「缺评测自动化，每次都要手写脚本」。代码里指标散落在 `eval.py`、`cap_eval_beam.py`、`report_*.py`、各训练脚本的 `print` 里，没有统一入口、没有基线文件、没有「跑一次出全部指标」的能力。没有可靠评测，scaling 是否真的失败、问答是否真的跑题都无法量化锁定，其它所有改进都无从验证。

**修法**：
1. 建一个统一评测入口 `eval_all.py`（或复用现有 `eval.py` 扩展），一键跑出所有模态的指标，输出到 `logs/baseline.json`。
2. 固定指标口径：图像 chrF、声音识别准确率、声音分类准确率、问答内容准确率、检索 R@1/R@5、端到端延迟，每项附「数据集 + 评测脚本 + 随机种子」。
3. 把 Issue 里的基线数字落盘成 `docs/baseline.md` 或 `logs/baseline.json`，作为后续改进的唯一对照。
4. （可选）一个 `eval_job.sh` 已存在，扩展成「训练后自动跑评测」的钩子。

**预估工作量**：**0.5～1 天**。纯工程，不涉及模型训练。

**验收判据**：`python3 eval_all.py` 一条命令产出全部指标与基线文件；新跑出的数字与 Issue 基线可对账（允许环境差异，记录差异原因）。

---

### 问题二：声音 VQ 量化塌缩（明确 bug、有现成修法）

**现状**：Issue 写「声音 VQ 量化塌缩，码本只用 1 个码字」。`amae.py` 是反面案例（`emb.weight.data.uniform_(-1/K,1/K)` 初始化 + 无归一化，易塌缩）。`amae2.py` 已经写了修正：**k-means 预热码本、潜变量 L2 归一化、死码复活、训练 12000 步、逐码本打印使用率**。但 Issue 把 amae 系列记作「留作反面案例」，说明塌缩问题**尚未验证已彻底解决**——修正有没有真正让码本利用率上到 64/64，需要评测确认。

**修法**：
1. 先用 `amae2.py` 的最终评测逻辑复跑一次，记录「码本使用率 / 重建 MSE / 往返一致性 / 分频段误差」，确认是否还塌缩。
2. 若仍塌缩，按投入递增依次尝试：EMA 更新码本（替代「整表重随机」）、`ε`-entropy 正则、`commitment loss` 权重调优、码本维度降维。
3. 把「码本利用率」设为固定评测指标，纳入问题一的 `eval_all.py`，防止回退。

**预估工作量**：**1～2 天**（含复跑确认与可能的码本更新改造）。

**验收判据**：3 个码本 × 64 码字，每个码本使用率 > 50%（或明确记录仍塌缩的码字比例），重建 MSE 不显著劣于连续潜变量基线。

---

### 问题三：问答内容准确率低（约 27%，跑题）

**现状**：Issue 写「问答内容准确率只有约 27%，回答常跑题」。`report_overview.py` 里也承认「格式能学，事实装不下；推理能力目前为零」。`api_server.py` 的 `/api/ask` **目前根本没用模型**，是一个硬编码 `KNOWN` 规则表（法国首都 / 2+2 / 罗密欧），说明问答还没接真模型。仓库里没有 `sft*.py`（Issue 提到的指令微调脚本缺失）。

**修法（先诊断、后修）**：
1. **诊断**（不改模型，先定位跑题原因）：
   - 跑一个固定问答测试集，把「跑题」分成几类：词表 OOV、格式错乱、事实缺失、重复/退化。
   - 确认「27%」与「54.6%」哪个是当前真实数字，统一口径（见问题一）。
2. **按诊断结果对症修**（投入递增）：
   - 若词表覆盖不足 → 用 `tok_qa.py` 思路重建问答域词表；
   - 若格式没学稳 → 补指令微调数据（Issue 提到 alpaca/orca，`check_data.py` 也引用 `orca_big.npy`）；
   - 若事实装不下 → 明确「事实型问答不是 13.6M 模型的目标」，把产品定位收窄为「模板/结构型回答 + 已见知识」，而非追求闭卷事实问答。
3. 把 `/api/ask` 从硬编码规则表换成真模型（SFT 后接上）。

**预估工作量**：**2～4 天**（诊断 0.5 天，数据/词表/微调按诊断结果 1.5～3.5 天）。

**验收判据**：统一口径后，问答内容准确率有可复现的基线，并明确「本轮能提升到的目标值」与「明确不做的事实问答边界」。

---

### 暂不排入本轮：统一模型 scaling 失败（阶段四方向）

**现状**：Issue 写「数据 ×3.8、步数 ×2.5、参数 ×2.3 后指标反而下降」。`ARCHITECTURE.md` 已诊断根因是**架构缺陷**（v3 平均池化导致条件向量塌缩、文本解码器看不到画面），并规划了 v4（注意力池化 + 全局工作空间 + 输出路由 + 自评头），且明确要求**先验证三个假设**再继续：

1. 注意力池化能否把 z 的余弦降到 0.7 以下；
2. 工作空间迭代能否让「图→文」从随机升到可识别；
3. 自评头置信度是否真与误差相关。

**为什么排后**：这是投入最高、风险最高的一项，且作者自己的设计文档已要求「任何一个假设失败就停在那一步改设计」。应先完成问题一（评测）落地，让每个假设有量化判据，再动 scaling。

**方向**：完成前三项后，按 `ARCHITECTURE.md` 的 S1→S5 训练课程逐阶段验证，每阶段过判据才进下一阶段。

## 4. 评测方案（怎么自动跑、怎么记录基线）

### 4.1 目标

一条命令、一个基线文件、可对账、可回退。

### 4.2 方案

1. **统一入口**：新建 `eval_all.py`，参数 `--ckpt`、`--data`、`--seed`，聚合以下评测并输出 `logs/baseline.json`：
   - 图像描述 chrF（复用 `cap_eval_beam.py` 的 `chrf` 实现）
   - 统一模型：重建 MSE/PSNR、检索 R@1/R@5、生成字符准确率（复用 `eval.py`）
   - 声音：分类准确率、VQ 码本利用率、重建 MSE（复用 `amae2.py` 的评测段）
   - 问答：内容准确率（统一口径，固定测试集）
   - 端到端延迟（ASR/模型/TTS 分段计时，复用 `stream_pipeline.py` 思路）
2. **基线落盘**：每次跑完把 `baseline.json` 归档为 `logs/baseline_<日期>.json`，`logs/baseline.json` 永远指向最新。Issue 里的历史数字写进 `docs/baseline.md` 作为对照。
3. **可复现**：固定随机种子、固定测试集切分（沿用各脚本已有的 `perm`/`tr`/`te` 切分方式）、记录依赖版本。
4. **训练后自动跑**：把 `eval_job.sh` 扩成「训练结束 → 自动 `eval_all.py` → 写入基线」，实现「改完代码跑一遍就知道是进步还是退步」。

### 4.3 记录基线的最小格式

```json
{
  "date": "2026-11-17",
  "ckpt": "ckpt/model.pt",
  "metrics": {
    "caption_chrF": 59.7,
    "sound_classify_acc": 93.9,
    "vq_codebook_usage": [64, 64, 64],
    "qa_content_acc": 54.6,
    "e2e_first_audio_ms": 1747
  }
}
```

## 6. 风险与依赖

- **数据/权重不在仓库里**（`.gitignore` 排除 `data/`、`ckpt/`、`logs/`），复跑评测依赖树莓派或 Windows 训练机上的数据与权重；本计划只读代码，不涉及这些资产的搬运。
- **Issue 描述与仓库实际有出入**（缺失 `fastvocab2.py`、`pre3.py`、`sft*.py`、`unified.py`、`uni*.py`），后续按仓库实际文件为准，如需对齐 Issue 描述需先确认那些文件是否在别的分支/机器上。
- **两处指标口径不一致**（问答 27% vs 54.6%），阶段一必须先统一口径，否则后续改进无法量化判断。
- **训练硬件分工**：树莓派跑推理/前端、Windows 训练机跑重训练；修法涉及重训时需明确在哪个环境执行。
